# ПОС - Преподавательская оценка студентов

Консольное приложение для учёта студентов, критериев и оценок, расчёта итогового балла и экспорта ведомости. Учебный проект по КПО: DDD, Ports and Adapters и паттерны проектирования.

## Запуск

Нужен Go 1.23 или новее. Из корня проекта:

```powershell
go mod download
go run .
```

Сборка и проверки:

```powershell
go build -o pos.exe .
go test ./... -cover
go vet ./...
```

При первом скачивании зависимости `go.uber.org/dig` нужен доступ к сети. Приложение работает с файлами относительно текущего рабочего каталога, поэтому запускать его следует из корня проекта или отдельного каталога с подготовленными данными.

## Возможности и меню

| Пункт | Действие |
| --- | --- |
| 0 | Завершить работу |
| 1 | Показать ID и имена студентов |
| 2 | Добавить студента с уникальным ID |
| 3 | Показать критерии, максимальные баллы и веса |
| 4 | Добавить критерий |
| 5 | Выставить или исправить оценку: повторный ввод по тому же критерию заменяет прежний балл |
| 6 | Отменить оценку по критерию |
| 7 | Рассчитать итог студента по ID |
| 8 | Экспортировать итоги всех студентов в CSV или JSON |
| 9 | Показать выставленные оценки выбранного студента |

Вес вводится через точку, например `0.3`. Названия критериев и ID должны совпадать с сохранёнными значениями. Баллы и максимумы - целые числа. При пользовательской ошибке программа печатает сообщение и возвращает в меню.

Пункт 9 показывает критерий и балл с максимумом; если оценок нет, выводится отдельное сообщение.

## Хранение и экспорт

- `students.json` - студенты и их оценки; каждое изменение сохраняется сразу.
- `rubrics.json` - действующий рубрикатор. Именно это имя задано в `main.go`.
- `rubric.json` - дополнительный файл в проекте; приложение его не читает.
- `итоги.csv` - пример выгрузки.

Если файлов хранилища нет, репозитории возвращают пустые коллекции и создают файлы при первом сохранении. Повреждённый JSON приводит к ошибке чтения, а не к автоматическому сбросу данных.

Пункт 8 выбирает формат по расширению пути: `.csv` или `.json` (без учёта регистра). Неизвестное расширение отклоняется. CSV использует разделитель `;`, заголовок `студент;итог` и итог с одним знаком после точки. JSON содержит массив объектов с полями `студент` и `итог`. Пустая JSON-ведомость представлена как `[]`.

Форматтеры используют `encoding/csv` и `encoding/json`, поэтому кавычки, разделители и переносы строк в именах экранируются. Файл по указанному пути перезаписывается; родительский каталог должен существовать.

## Расчёт итога

Базовый доменный сервис `WeightedCalculator` считает:

```text
итог = 10 × Σ ((балл / максимум) × вес критерия)
```

В приложении он обёрнут в `RoundingCalculator`, который округляет результат до целого через `math.Round`. В консоли и CSV результат выводится с одним знаком после точки, например `8.0`.

Пример: домашние задания - 9/10 с весом 0.3, проект - 16/20 с весом 0.4, контрольная - 7/10 с весом 0.3. Итог: `10 × (0.9 × 0.3 + 0.8 × 0.4 + 0.7 × 0.3) = 8.0`.

Оценки по отсутствующим у студента критериям в сумму не входят: фактически их вклад равен нулю. Веса не нормализуются. Сумма весов может быть меньше 1, но не больше 1 с допуском `1e-9`; поэтому при неполном рубрикаторе максимальный возможный итог меньше 10. Итог не хранится отдельно: его пересчитывают по текущим оценкам и рубрикатору.

## Карта DDD и логика решений

Единый язык предметной области отражён в именах типов: `Student` - студент, `Criterion` - критерий, `Evaluation` - оценка, `Rubric` - рубрикатор, `FinalGrade` - итог.

| Роль | Реализация и обоснование |
| --- | --- |
| Entity | `Student`: идентичность задаёт ID, имя и оценки могут изменяться |
| Корень агрегата | `Student` владеет оценками, индексированными названием критерия; изменение и отмена проходят через его методы |
| Корень агрегата | `Rubric` владеет критериями и проверяет уникальность названий и сумму весов |
| Entity внутри рубрикатора | `Criterion` идентифицируется уникальным в рубрикаторе названием; идентичность сохраняется при изменении параметров |
| Value Object | `Score`, `Weight`, `FinalGrade`: значения с ограничениями, без самостоятельного ID |
| Объект-значение оценки | `Evaluation`: пара «критерий + балл», без отдельного ID; исправление заменяет объект в агрегате студента |
| Repository - порт | `StudentRepository`, `RubricRepository` объявлены в домене; JSON-реализации находятся снаружи |
| Domain Service | `GradeCalculator` / `WeightedCalculator`: расчёт использует и студента, и рубрикатор, поэтому вынесен из одной сущности |
| Фабрика | `EvaluationFactory`: создаёт оценку по критерию рубрикатора и проверяет диапазон балла |

Например, два студента с одинаковым именем и разными ID - разные сущности. Два `Score` с одинаковыми баллом и максимумом выражают одинаковое значение.

Основные проверки модели:

- `Student`: непустые ID и имя; сценарий добавления отдельно проверяет уникальность ID через репозиторий.
- `Criterion`: непустое название и положительный максимум.
- `Score`: `0 <= value <= max`, `max > 0`.
- `Weight`: `0 < weight <= 1`; `NaN` и бесконечности отклоняются.
- `Rubric.AddCriterion`: название не повторяется, сумма весов не превышает 1 с допуском.
- `EvaluationFactory.Create` и `NewEvaluation`: критерий существует в рубрикаторе, балл соответствует его максимуму.
- `Student.SetEvaluation`: повторная проверка оценки по переданному рубрикатору, включая защиту от нулевых объектов.
- Загрузка и сохранение студента проверяют оценки по действующему рубрикатору, а не доверяют содержимому JSON. Ошибка поиска студента `ErrStudentNotFound` отделена от ошибок чтения.
- `FinalGrade`: диапазон от 0 до 10; `NaN` и бесконечности отклоняются.

Домен содержит поведение и проверки, а не только DTO. DTO в `infrastructure/dto.go` нужны исключительно для сериализации: закрытые поля модели напрямую в JSON не экспортируются.

## Архитектура: Ports and Adapters

Используется облегчённая слоёная реализация без отдельных модулей и микросервисов.

```text
domain/          - сущности, объекты-значения, агрегаты, фабрика,
                   сервис расчёта и порты репозиториев
application/     - сценарии добавления, просмотра, выставления,
                   отмены, расчёта и экспорта; порт GradeExporter
infrastructure/  - JSON-репозитории, DTO, файловый экспорт и форматтеры
main.go          - входной консольный адаптер и composition root
```

Зависимости исходного кода направлены внутрь:

```text
application → domain
infrastructure → application, domain
main → application, infrastructure, domain
```

`domain` не импортирует консоль, JSON, файловую систему, инфраструктуру или DI-фреймворк. Сценарии зависят от портов, а конкретные адаптеры подключаются при сборке приложения.

DI-контейнер `go.uber.org/dig` создаётся в `main()`. Через `Provide` регистрируются репозитории, калькулятор, экспортёр, use cases и `App`; `Invoke(run)` запускает консоль. Конкретные пути файлов и выбор стратегии задаются здесь же. Сценарии получают зависимости через конструкторы, не обращаются к контейнеру как к глобальному сервису.

## Паттерны проектирования

| Группа | Паттерн | Где и какую задачу решает |
| --- | --- | --- |
| Порождающий | Фабрика (Simple Factory) | `EvaluationFactory.Create`: единая точка создания оценки с поиском критерия и проверкой балла; UI не повторяет эти проверки |
| Структурный | Decorator | `RoundingCalculator` реализует `GradeCalculator` и оборачивает другой калькулятор; округление добавляется без изменения взвешенной формулы и use cases |
| Поведенческий | Strategy | Порт `GradeCalculator` отделяет сценарии от алгоритма итога; `GradeFormatter` позволяет одному `FileExporter` использовать CSV- или JSON-форматирование |

У калькулятора сейчас одна базовая формула; округляющая обёртка - декоратор, а не вторая самостоятельная формула. У форматирования есть две реализации стратегии. `ExtensionExporter` выбирает их по расширению файла в каждом запросе на выгрузку; калькулятор подключается в composition root.

`EvaluationFactory` - простая фабрика; она не реализует GoF Factory Method с переопределением метода в подклассах. Это соответствует приведённому в задании примеру фабрики оценок, но такое различие важно при объяснении решения на защите. `FileExporter` использует композицию со стратегией форматирования, поэтому называть его классическим Template Method с наследованием было бы неточно.

## Сквозная демонстрация

Чтобы не менять примеры из репозитория и не столкнуться с повторными ID и суммой весов, можно собрать приложение и запустить его в отдельном пустом каталоге:

```powershell
# Из корня проекта
go build -o pos.exe .
$demoDir = Join-Path $env:TEMP ("pos-demo-" + [guid]::NewGuid().ToString())
New-Item -ItemType Directory -Path $demoDir | Out-Null
Copy-Item .\pos.exe $demoDir
Push-Location $demoDir
.\pos.exe
# После выхода из приложения:
Pop-Location
```

В меню последовательно:

1. Пункт 2: ID `demo-001`, имя `Иванов Иван`.
2. Трижды пункт 4: `Домашние задания`, максимум `10`, вес `0.3`; `Проект`, максимум `20`, вес `0.4`; `Контрольная`, максимум `10`, вес `0.3`.
3. Пункты 1 и 3: проверить студента и рубрикатор.
4. Трижды пункт 5: студент `demo-001`, по указанным критериям баллы `9`, `16`, `7` соответственно.
5. Пункт 9: ID `demo-001`, проверить три выставленные оценки. Затем пункт 7 с тем же ID: ожидаемый итог `8.0`.
6. Пункт 8: путь `итоги.csv`. Ожидаемое содержимое:

```csv
студент;итог
Иванов Иван;8.0
```

Повторите пункт 8 с путём `итоги.json`, чтобы проверить второй формат.

Дополнительно можно проверить отклонение балла `21` для проекта и неизвестного критерия. Повторный пункт 5 исправляет оценку, пункт 6 её отменяет; после отмены расчёт изменится. После выхода и повторного запуска в том же каталоге сохранённые данные остаются доступны.

## Проверки

```powershell
go test ./... -cover
go vet ./...
go build .
```

Тесты проверяют:

- границы балла и веса, запрет `NaN` и бесконечности;
- уникальность критериев и ограничение суммы весов;
- создание оценки только по существующему критерию и с правильным максимумом;
- защиту агрегатов от изменения через возвращаемые коллекции;
- взвешенный итог, округление, исправление и отмену оценки;
- сквозной сценарий с реальными JSON-репозиториями во временном каталоге;
- повторную загрузку данных и отклонение неверных оценок в хранилище;
- сохранность повреждённого файла при неудачном добавлении студента;
- CSV/JSON с кавычками, разделителями и переносами строк в именах;
- пустой JSON-экспорт и отклонение неизвестного формата.

## Границы решения

Это однопользовательское локальное приложение: JSON-файлы не предназначены для одновременной записи несколькими процессами. Между отдельными файлами нет транзакции. ID студентов и названия критериев сравниваются с учётом регистра. Порядок критериев в обычном списке не гарантирован, оценки в пункте 9 отсортированы по названию.

Изменение и удаление студентов/критериев в задании оставлены на усмотрение разработчика. Импорт, дата и комментарий оценки, несколько курсов и пересдачи не входят в текущее ядро. Аналитика представлена расчётом и выгрузкой итогов.
